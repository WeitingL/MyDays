## Feature Brief

> 由我填寫。

想在 MyDays 加入習慣養成功能，要能容易上手、UI 清楚。核心能力：

- 建立習慣並設定執行頻率
- 每天打卡記錄執行狀況
- 支援「養成好習慣」與「戒除壞習慣」兩種面向
- 支援執行內容會輪替的習慣（例如保養習慣，但保養品有不同輪替組合）
- 顯示連續執行天數（streak）
- 推播提醒

不包含：改動 App 既有視覺風格、與其他功能的交互整合。

---

## Design Review

> 由 Agent 整理，以下為 Brief 中已明確、可直接定案的方向。

- **頻率設定**：支援四種模式 — 每日、每 N 天、每月指定日期、每週指定星期幾（以一週區間讓使用者勾選）
- **打卡方式**：單純打勾（完成 / 未完成），不做數量輸入
- **資料儲存**：Room + Firestore 雙層同步（離線優先，背景同步）
- **功能入口**：功能 Tab 新增一張 FeatureCard，與 Todo 並列
- **統計視覺化**：以 streak 為主要指標；streak 依頻率型別給不同呈現（每日→天、每 N 天→次、每週→週、每月→月）
- **Streak 演算法**：好習慣（連續完成）與壞習慣（距上次破戒天數，無紀錄=成功）為兩套獨立邏輯
- **壞習慣打卡**：預設成功，僅記錄「破戒」（Ambiguity 2 決議 A）
- **推播提醒**：需要，使用者可為習慣設定提醒；壞習慣提醒策略獨立（可能預設關閉，避免誘導破戒）
- **輪替型習慣**：不納入 MVP，先獨立出 component 設計以利日後擴充（Ambiguity 1 決議 B）
- **視覺風格**：沿用現有 Liquid Glass 風格，不另設計

## Ambiguities

> 由 Agent 指出待釐清處，每項附方案與建議供選擇。

1. **輪替型習慣（如保養品組合）是否納入 MVP**
   - 方案 A（納入 MVP）：一個習慣下可掛多個「執行組合」，打卡前先選今日組合。需擴充資料模型與打卡 UI，與「單純打勾」衝突。
   - 方案 B（未來擴充）：MVP 先做單純打勾，輪替機制列為後續 phase。
   - 建議：**方案 B**。輪替是進階需求，先確保核心打卡體驗穩定，避免 MVP 過度複雜。
   - 決議：B （我覺得這個可以先建立獨立的 component 文件設計，之後比較好修改）

2. **「戒除壞習慣」的打卡邏輯**
   - 方案 A（預設成功）：系統每天預設為「成功（沒做）」，使用者主動按「今天破戒了」才記失敗。
   - 方案 B（主動打卡）：與養成習慣相同，每天主動打卡，語意為「今天有守住」。
   - 建議：**方案 A**。戒除類習慣的心理模型是「維持不做」，預設成功、只記錄破戒，符合直覺且降低打卡負擔。
   - 決議：A 同意，因為一直提醒會變成一種吸引用戶破戒的操作。

3. **非每日習慣的 Streak 計算單位**
   - 方案 A（以週期計）：只要在該週期（週 / 月）內達標，連續週期數 +1。
   - 方案 B（以天計）：嚴格計算連續天數，漏一天即中斷。
   - 建議：**方案 A**。頻率既然允許「每週幾次」，streak 應對齊使用者設定的週期，否則非每日習慣的 streak 幾乎無法維持。
   - 決議：A 跟 B 應該要共存，依照頻率的設定給予不同的統計呈現方式。

## Proposed Phases

> 由 Agent 提案，MVP 優先。待 Ambiguities 決議後可能微調。

### Phase 1 — 核心打卡（MVP）
- 新增 / 編輯 / 刪除習慣（含頻率設定：每日 / 每 N 天 / 每月指定日 / 每週指定星期）
- 好習慣 / 壞習慣兩種類型
- 每日打卡（單純打勾）
- Streak 顯示
- 本地 Room 儲存

### Phase 2 — 雲端同步
- Firestore 資料模型與同步機制
- 離線優先、背景同步、衝突處理

### Phase 3 — 提醒通知
- 每個習慣可設定提醒時間
- 推播排程與權限處理

### Phase 4 — 輪替型習慣（進階，視需求）
- 習慣下的執行組合管理
- 打卡前選擇今日組合
