# CONVENTIONS

開發過程中總結出的設計原則。每條都附「為什麼」——通則會被遺忘，但理由能讓人重新推導出通則。

**為什麼有這份文件**：避免「上次討論過了但這次又犯同樣錯誤」。
寫在這裡的東西不需要重講。

**維護方式**：從實際開發中發現問題後，與船長（Weiting）討論確認後寫入。不主動新增。

---

## 1. 「達成」不可綁死在 UI 動作上

任何模組判定「這件事完成了」時，判定條件不可寫成「使用者在本模組頁面按了某個按鈕」。
完成是一個**事實**，按鈕只是回報它的其中一種管道。

**判準**：如果別的模組也能促成這件事完成，現在的寫法接得上嗎？
接不上 → 要改。

**這條只要求「不要寫死」，不要求現在就蓋擴充點。**
預先抽 interface、設事件總線、加來源欄位都屬過度設計。本條的實作成本應該是零；
若某次改動為了滿足本條而需要新增檔案或欄位，那就是誤讀了。

**為什麼**：模組之間會互相引用完成事件（在健身模組做完運動，習慣模組也該算達成）。
一旦完成判定與 UI 動作綁死，日後要接就得動判定邏輯本身——
而那時判定邏輯通常已經有好幾份 spec 依賴它，改動的代價遠高於一開始就留白。

**訂於**：2026-08-08（起因：habit feature 討論「健身模組完成運動也算習慣達成」，
確認是未來需求，決定只保留彈性、不現在實作）

## 2. 寫入動作的反饋不可依賴資料變化

任何「按下去會寫入」的控制項，它的視覺反饋**不可只來自寫入後的資料變化**。
按鈕自己就要有反饋，寫入成功與否是另一回事。

**判準**：連按同一個動作兩次——第二次還看得到反饋嗎？
看不到 → 要改。

**為什麼**：寫入常常是幂等的（同日重複打卡是復活同一筆記錄），邊界值也常常不變
（streak 為 0 時天數句不會動）。把反饋綁在資料變化上，等於**在最需要確認的情況下
剛好沒有確認**——使用者按了、事情也真的做了，但畫面完全沒動，只能再按一次。

**訂於**：2026-08-09（起因：`habit-counting-mode` Gate 2——「今天發生了」按鈕在
streak 為 0 時零反饋。設計當時的反饋論證是「天數句會變」，卻被同一份設計的
邊界條件 4「同日重複按是幂等的，streak 維持 0」直接反駁，而沒有任何 AC 要求可感知的反饋）
