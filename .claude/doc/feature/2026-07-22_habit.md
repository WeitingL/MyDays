## Feature Brief

> 由我填寫。（2026-08-08 授權 Agent 依 Phase 4 決議代改用語）

連續型習慣：一件事 + 一種「什麼算達成」的定義，累積連續天數。兩種模式：

- **每天都做**（如：每天運動）→ 顯示「連續 12 天做了」
- **克制不做**（如：克制亂花錢）→ 顯示「連續 12 天沒做」

兩種都是我做到的事，都要被肯定。不分好壞，不譴責。

特性：單一內容、每日執行、以「連續天數」為核心價值。

**範圍收窄**：
- 「依星期做不同內容」（如一週運動組合）移到獨立的「一週計劃」feature。
- 「同一習慣多子項目 + 輪替」（如保養）為更後續，兩個 feature 穩定後再處理。

## Design Review

> 由 Agent 整理，已明確定案的方向。
> ⚠️ 2026-08-08 修訂：原本的「好習慣 / 壞習慣」分類已取消，見下方。

- **核心概念**：一個習慣 = 一件事 + 一種「什麼算達成」的定義。
  兩種模式**都是成就**，都要被肯定
- **兩種模式**（建立時選一種，**必須區分**，顯示的數字語意不同）：
  - **每天都做** — 每天打勾，顯示「連續 N 天做了」，漏一整天歸零（例：每天運動）
  - **克制不做** — 事情發生時記一次，顯示「連續 N 天沒做」（例：克制亂花錢）
- **取消的是負面包裝，不是區分本身**：不再稱任何一種為「壞習慣」，
  不再出現「破戒」這類自我譴責的字眼與禁止類圖示
- **語氣分工**：
  - **數字** → 正向肯定，兩種模式皆是（連續 12 天做了 ✅／連續 12 天沒做 ✅）
  - **記錄按鈕** → 中性，只登記事實，不評價
- **稱讚時機**：日常只靠視覺（顏色、圖示、排版）呈現正向，
  文字稱讚只在里程碑 **7 / 30 / 100 天**出現
- **不設間隔限制**：不做「每 N 天才能一次」的上限、倒數或阻擋，由我自己看數字判斷
- **打卡方式**：每天都做 → 每日打勾；克制不做 → 事情發生時記一次
- **資料儲存**：Room + Firestore 雙層同步
- **功能入口**：功能 Tab 的 FeatureCard（既有停用入口 `Icons.Default.Loop`）
- **推播提醒**：需要；「克制不做」模式的提醒策略獨立（可能預設關閉——提醒「你已經 12 天沒做這件事」容易反效果）
- **視覺風格**：沿用 Liquid Glass，不另設計
- **內容模型**：單一內容，**無 variant、無依星期變化**（那些歸「一週計劃」）

### 2026-08-08 修訂的原因

兩種模式**本來就該區分**——「每天運動連續 12 天」和「12 天沒亂花錢」是不同的數字，
心裡的感受也不同。原設計的問題不是它做了區分，而是**只有一側是正面的**：

| | 原設計 | 問題 |
|---|---|---|
| 想每天做 | 「養成好習慣 · 連續 12 天」 | 沒問題 |
| 想克制不做 | 「戒除壞習慣 · 已 12 天未破戒」＋「破戒」按鈕＋禁止圖示 | 我明明也做到了 12 天，卻被寫成一件關於失敗的事 |

兩邊都是我做到的事，都該是「很棒」。要拿掉的是**單側的負面包裝**，
不是區分，也不是價值判斷——價值判斷要留，而且兩邊都要是正的。

計算邏輯本身完全正確（`buildStreak` / `quitStreak` 都在跑），壞的只有包裝。

## 對外接點（未來，不在目前任何 Phase 內）

> 2026-08-08 記錄意圖與約束，**現在不實作**。寫在這裡是為了不被忘記，
> 不是為了現在動工——下游 agent 不得依此蓋抽象層。

**意圖**：其他模組的完成事件也能算作這裡的「達成」。
例：在健身模組完成今天的運動 → 對應的習慣自動記一次達成。

**現在唯一要守的約束**（已升級為 `CONVENTIONS.md` #2）：
「達成」不可綁死成「使用者在 habit 頁面按了按鈕」。核心概念句
「一個習慣 = 一件事 + 一種『什麼算達成』的定義」本身已經預留這個位置，
達成的**來源**是開放的——不需要額外設計就已經有彈性。

**現在刻意不做**：
- 不設事件總線、不抽 interface、不加來源欄位
- `CheckIn` 是否需要「來源」欄位 → 留到真要做時再決定。
  延後成本低：Room 端用 destructive migration，Firestore 端缺欄位可視為預設值

**不屬於這裡**：「App 主動鼓勵用戶」是主頁面「今天摘要」的事，
等主頁面 feature 開檔時再記，不寫進 habit（否則以後做資料接點會順手把呈現一起做掉）。

## Ambiguities

> 由 Agent 指出待釐清處，每項附方案與建議。

1. **streak 中斷後如何呈現**
   - 方案 A：直接歸零，只顯示目前連續天數
   - 方案 B：歸零，但保留「歷史最佳連續天數」
   - 建議：**方案 B**。保留最佳紀錄對習慣養成有正向激勵，欄位成本低。
   - 決議：**方案 A**（2026-08-08 回填）
   - ⚠️ 此決議當初未寫回本文件，實作已按 A 完成（`HabitEntity` 無 `bestStreak` 欄位），
     與上方建議的 B 相反。2026-08-08 review 時發現並補記，維持 A。

2. **是否允許補打卡（回補前幾天）**
   - 方案 A：只能打卡當日，最單純
   - 方案 B：允許回補近 N 天，streak 需重算
   - 建議：**方案 A** 作為 MVP，降低 streak 計算複雜度；補打卡列未來。
   - 決議：**方案 A**（2026-08-08 回填；原記於 `habit-checkin-streak` spec Open Q1）

3. **兩種計數模式對使用者顯示的名稱**（2026-08-08 新增）
   - 方案 A：「連續幾天做了」／「連續幾天沒做」
   - 方案 B：「養成」／「克制」
   - 方案 C：「做了算達成」／「沒做算達成」
   - 建議：**方案 A**。它是我口述的原話，而且**句式對稱**——
     兩邊都是「連續幾天」，天生就把兩種模式擺在同等地位，最符合「兩邊都是成就」的意圖。
     B 最短且都是正面詞，但「克制」仍隱含「有東西需要被克制」；C 精確但拗口。
   - 決議：**方案 A，並拆成兩處字串**（2026-08-08 船長授權 Agent 決定）
     - **選擇器**（建立習慣時選模式）：「每天都做」／「克制不做」——chip 塞得進去
     - **顯示句**（卡片副標）：「連續 N 天做了」／「連續 N 天沒做」——方案 A 原文
     - 理由：一個字串塞不進兩個位置。選擇器要短、要是動作；顯示句要對稱、要有數字。
       兩處都維持句式對稱，兩邊都是「我刻意在做的事」，沒有一側被貶。

4. **正向呈現要做到什麼程度**（2026-08-08 新增）
   - 方案 A：只在**視覺**上正向——顏色、圖示、排版讓數字看起來像成就，不加文字稱讚
   - 方案 B：**顯示鼓勵文案**，如「連續 12 天，很棒！」
   - 方案 C：視覺正向為主，僅在**里程碑**（7 / 30 / 100 天）出現稱讚
   - 建議：**方案 C**。你說「好棒喔！」「很棒！」時我不確定是要 App 真的講出來，
     還是只要那個感覺；每天都稱讚會很快變成噪音，里程碑稱讚比較保值。
   - 決議：**方案 C**（2026-08-08）。里程碑定為 **7 / 30 / 100 天**，兩種模式共用同一組。

## Proposed Phases

> 由 Agent 提案，MVP 優先。

### Phase 1 — 核心打卡（MVP）
- 新增 / 編輯 / 刪除習慣（兩種模式）
- 每日打卡（單純打勾）
- Streak 顯示（每天都做 → 連續完成天數；克制不做 → 距上次紀錄天數）
- 本地 Room 儲存

### Phase 2 — 雲端同步
- Room + Firestore 離線優先同步

### Phase 3 — 提醒通知
- 每個習慣可設提醒；「克制不做」模式的提醒策略獨立

### Phase 4 — 兩種模式改為正向呈現（2026-08-08 新增）
- **保留**兩種模式的區分，建立習慣時選一種
- 移除單側的負面包裝：「壞習慣」分類名、「破戒」字樣、禁止類圖示
- 兩種模式的連續天數都以正向方式呈現，都是成就
- 用語改為「每天都做 / 克制不做」（選擇器）與「連續 N 天做了 / 連續 N 天沒做」（顯示句）
- 里程碑 7 / 30 / 100 天出現文字稱讚，日常只靠視覺呈現正向
- 不動計算邏輯、資料同步與提醒機制
