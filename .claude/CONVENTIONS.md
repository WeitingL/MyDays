# CONVENTIONS

跨 spec 的長期通則。從討論或 loop 中長出來，經船長批准後寫入，之後所有 spec 與 agent 都受其約束。

**為什麼有這份文件**：一個人開發最痛的是「我上次跟 agent 講過了，但這是新對話」。
寫在這裡的東西不需要重講。每條都附「為什麼」——通則會被遺忘，但理由能讓人重新推導出通則。

**維護方式**：agent 在收尾時提議升級，船長批准才寫入。不主動新增。
若某份 spec 的需求違反此處通則，大副（`spec-partner`）必須指出，由船長裁決是遵守還是**明確地改通則**。

## 1. 文件層級：feature 管關係，spec 管自己

| 層 | 回答的問題 | 管轄範圍 |
|---|---|---|
| `doc/feature/` | 我這個生活面向要什麼？拆成哪幾次交付？ | 所有 spec 之間的關係與順序 |
| `doc/spec/` | 這一次交付什麼？完成長什麼樣？ | 只有自己 |

**判準**：這個決定會不會影響其他 spec？
會 → feature 層　　不會 → spec 層

**為什麼**：一份 feature 對應多份 spec。spec 只能決定自己，無權改動兄弟 spec 的前提。
把 feature 層的決定寫進 spec，其他 spec 的前提會悄悄失效——文件還寫著「已實作」，
但它依賴的假設已經被改掉了，而沒有任何地方記錄這件事。

**訂於**：2026-08-08（起因：`habit-limit` spec 撰寫途中決定重新設計整個習慣模組，
影響四份既有 spec，超出 spec 層權限，退回 feature 層處理）

## 2. 「達成」不可綁死在 UI 動作上

任何模組判定「這件事完成了」時，判定條件不可寫成「使用者在本模組頁面按了某個按鈕」。
完成是一個**事實**，按鈕只是回報它的其中一種管道。

**判準**：如果別的模組也能促成這件事完成，現在的寫法接得上嗎？
接不上 → 要改。

**這條只要求「不要寫死」，不要求現在就蓋擴充點。**
預先抽 interface、設事件總線、加來源欄位都屬過度設計。本條的實作成本應該是零；
若某次改動為了滿足本條而需要新增檔案或欄位，那就是誤讀了。

**為什麼**：模組之間會互相引用完成事件（在健身模組做完運動，習慣模組也該算達成）。
一旦完成判定與 UI 動作綁死，日後要接就得動判定邏輯本身——
而那時判定邏輯通常已經有好幾份 spec 依賴它，改動的代價遠高於一開始就留白。

**訂於**：2026-08-08（起因：habit feature 討論「健身模組完成運動也算習慣達成」，
確認是未來需求，決定只保留彈性、不現在實作）

## 3. 寫入動作的反饋不可依賴資料變化

任何「按下去會寫入」的控制項，它的視覺反饋**不可只來自寫入後的資料變化**。
按鈕自己就要有反饋，寫入成功與否是另一回事。

**判準**：連按同一個動作兩次——第二次還看得到反饋嗎？
看不到 → 要改。

**為什麼**：寫入常常是幂等的（同日重複打卡是復活同一筆記錄），邊界值也常常不變
（streak 為 0 時天數句不會動）。把反饋綁在資料變化上，等於**在最需要確認的情況下
剛好沒有確認**——使用者按了、事情也真的做了，但畫面完全沒動，只能再按一次。

**訂於**：2026-08-09（起因：`habit-counting-mode` Gate 2——「今天發生了」按鈕在
streak 為 0 時零反饋。設計當時的反饋論證是「天數句會變」，卻被同一份設計的
邊界條件 4「同日重複按是幂等的，streak 維持 0」直接反駁，而沒有任何 AC 要求可感知的反饋）

## 4. 「不動某檔」必須與 AC 的禁止清單交叉檢查

設計裡任何「這個檔案／這幾行完全不改」的宣告，寫下之前要對照 AC 的禁止清單，
確認被宣告為不改的那些行**沒有落在禁止範圍內**。

**判準**：AC 有「全 App 不得出現 X」這類條件時，每個被宣告「不改」的檔案都要 grep 過 X。

**為什麼**：「不改」與「不得出現」互斥時，實作者照設計做就必然違反 AC，照 AC 做就必然
違反設計——他**無論怎麼選都是錯的**，而錯會記在他頭上。這種矛盾只有設計階段能消除，
到了實作階段已經沒有正確答案。

**訂於**：2026-08-09（起因：`habit-counting-mode` Round 1——`Framework` 宣告
`HabitWithStreak.kt:26-29` 完全不改，但 AC 禁止 `relapse` 識別字，
而 `relapseDays` 就在那幾行）
